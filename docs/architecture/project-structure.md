## Architecture Overview

This project follows **Clean Architecture**. Dependencies always point inward:

```
HTTP Handler  →  Usecase  →  Repository  →  Database
     ↑               ↑            ↑
  (parser,       (entity        (GORM /
  presenter)      DTOs)         MongoDB)
```

Each layer has a single responsibility:

| Layer | Location | Responsibility |
|---|---|---|
| **Handler** | `internal/http/handler/` | Parse HTTP input, call usecase, return response |
| **Usecase** | `internal/usecase/` | Business rules, validation, orchestration |
| **Repository** | `internal/repository/` | Data access — query/write to DB or cache |
| **Entity** | `entity/`, `internal/*/entity/` | Data transfer objects — no logic |

## Three Runnable Services

### 1. API (`cmd/api/main.go`)
REST API server built on [Fiber v3](https://github.com/gofiber/fiber).

- Boots MySQL, wires repositories → usecases → handlers
- Registers routes under `/api/v1/`
- Exposes `/apidoc/*` (Swagger UI), `/metrics` (process stats), `/health-check`
- Graceful shutdown on `SIGTERM`/`SIGINT` with a 30-second drain timeout

### 2. Worker (`cmd/worker/main.go`)
RabbitMQ consumer. Topic key is passed as a CLI argument:

```bash
go run cmd/worker/main.go sync.log
go run cmd/worker/main.go example.process
```

- Connects to MongoDB and RabbitMQ on startup
- Dispatches to the matching consumer based on the topic
- Automatically reconnects on connection drop

### 3. Scheduler (`cmd/scheduler/main.go`)
Background job runner powered by [gocron v2](https://github.com/go-co-op/gocron).

- Jobs defined using `DurationJob` or cron expressions
- Runs in the foreground indefinitely via `select{}`
- Can optionally connect to RabbitMQ to enqueue async work

## Key Design Patterns

### Transaction Support
`internal/repository/mysql/gorm.go` provides `DBTransaction`, a helper that wraps any multi-step DB operation in a single atomic transaction with automatic rollback on error:

```go
err = mysql.DBTransaction(repo, func(trx mysql.TrxObj) error {
    if err := repo.LockByID(ctx, trx, id); err != nil {  // SELECT ... FOR UPDATE
        return err
    }
    return repo.Update(ctx, trx, params, changes)
})
```

Isolation level is `READ COMMITTED`. Pessimistic locking (`FOR UPDATE`) is used where race conditions are possible.

### Interface-driven Dependencies
Every repository and usecase exposes an interface (e.g. `ITodoListRepository`, `ITodoListUsecase`). This enables:
- Unit testing with generated mocks (no real DB needed)
- Swapping implementations without changing callers

### Mock Generation
Mocks are auto-generated by [mockery](https://github.com/vektra/mockery) based on `.mockery.yaml`. Run with:

```bash
make mock-gen
# or
mockery
```

Generated files live in `tests/mocks/`.

### Validation
Struct validation uses [go-playground/validator](https://github.com/go-playground/validator) with Indonesian locale translations. The `ValidateStruct` helper in `internal/usecase/usecase.go` returns a JSON-encoded error string consumed by the presenter layer.

## JWT Authentication

`internal/http/auth/jwt.go` supports two signing methods, toggled via the `JWT_SIGNING_METHOD` env var.

| Method | Env value | Algorithm | Keys required |
|---|---|---|---|
| RSA (default) | `rsa` | RS512 | `JWT_PRIVATE_KEY_PATH`, `JWT_PUBLIC_KEY_PATH` |
| HMAC | `hmac` | HS512 | `JWT_SECRET_KEY` (min 32 chars recommended) |

### RSA mode (default)
```env
JWT_SIGNING_METHOD=rsa
JWT_PRIVATE_KEY_PATH=private_key.pem
JWT_PUBLIC_KEY_PATH=public_key.pem
```
Generate keys: `openssl genrsa -out private_key.pem 2048 && openssl rsa -in private_key.pem -pubout -out public_key.pem`

### HMAC mode
```env
JWT_SIGNING_METHOD=hmac
JWT_SECRET_KEY=your-secret-key-min-32-chars
```

### Token usage
All protected endpoints read the `Authorization` header. The `Bearer ` prefix is optional — both formats are accepted:
```
Authorization: Bearer <token>
Authorization: <token>
```

Functions exposed: `GenerateToken`, `VerifyToken`, `RefreshToken`.
